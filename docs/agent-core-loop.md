# sala — Agent 核心能力闭环（讨论稿 v0.1）

> **状态：提案 / 待讨论，不是已确认的产品决策、V1 承诺或技术架构。**
>
> 目的：把已经确认的创作原则转化为可检查、可推翻的 Agent 能力需求。本文不锁定模型、运行时、UI、后端服务、数据模式或开发排期。
>
> 来源：[`product-vision.md`](product-vision.md)、[`interaction-principles.md`](interaction-principles.md)、[`capability-landscape.md`](capability-landscape.md) 与 `../.agnir/decisions.md`。新增细节均为 **待验证的设计建议**。

## 1. 核心命题

sala 不是「LLM 替用户生成提示词后点击视频生成」；期望 Agent 能持续维护人与 Agent 之间的**创作共识**，根据共识选择动作、执行、评估并迭代。

一个合格的闭环应对每轮变化回答：

1. **目标是什么？** 用户希望作品最终呈现什么。
2. **范围是什么？** 哪个片段、对象、属性需要变化，哪些必须保留。
3. **依据是什么？** 与哪些原始参考、已确认方案、已生成作品或用户反馈关联。
4. **怎么执行？** 选择什么能力、依赖、失败回退以及授权边界。
5. **如何判断？** 目标是否达成、非目标是否受影响、还有哪些不确定性。
6. **下一轮继承什么？** 哪些创作约束、产物和判断已经被接受或否定。

成功标准是「能跨轮维护可追溯的创作约束并实现有针对性的改动」，而不是单纯“成功调用模型”。

## 2. 六阶段闭环（建议模型）

### 阶段 A — 理解创作意图

**输入：** 自然语言指令、当前作品与版本、可能的参考图/视频、先前确认与否定的反馈。

**Agent 要做：** 将用户语句分解为创作目标、指认范围、明确变化项、必须保持项、可自由发挥项、待澄清项；区分用户明确说过的硬约束与 Agent 自己推断的假设。

**输出：** 一份逻辑上的「创作意图记录」（不规定 JSON 格式），包含：

- `goal`：期望的效果；
- `scope`：作品版本 / 时间 / 区域 / 对象；
- `change`：必须发生的变化；
- `preserve`：不得未经允许改变的内容；
- `freedom`：可由 Agent 自主决定的维度；
- `references`：目标与素材、过往决策的对应关系；
- `uncertainty`：事实不足、语义歧义、不可实现风险；
- `status`：假设 / 待确认 / 已确认 / 被否定。

**禁止混淆：** 用户没有提及的参数不等于已授权随意修改；Agent 的猜测不等于用户确认。

### 阶段 B — 分析参考素材

**输入：** 参考图片、视频、当前作品、已确认的创作意图。

**Agent 要做：** 在任务需要时分析镜头分段、时间关系、主体与对象、构图、运动、镜头路径、风格；建立用户语言与参考对象之间的对应。明确可直接观察的信息与推断信息。

**输出：** 逻辑上的「参考映射」：证据来源、时间区间 / 区域 / 对象、待保留维度、观察结果、不确定性。

**边界：** 不能把仅凭视频估计的深度、姿态、轨迹或三维空间关系表述为确定真值；真实 3D 重建与白模编辑仍是独立待研究方向。

### 阶段 C — 澄清并制定执行计划

**输入：** 创作意图记录、参考映射、可用能力、执行成本和限制。

**Agent 要做：**

1. 判断歧义是否影响主要创作方向或硬约束；**关键意图不清时先澄清**，与既有决策 D-006 一致。
2. 对非关键、低影响的缺口可提出显式假设，避免机械追问；是否允许直接执行须后续明确。
3. 将任务分为可独立完成、可验证的步骤，注明每步所需的能力类型、输入/输出、预估代价、失败回退和可保留的中间产物。
4. 若预计不能满足硬约束，执行前说明风险并寻求选择，不得默默放宽约束。

**输出：** 逻辑上的「执行方案」和必要的轻量澄清 / 可视化候选。**此处不规定采用某种框架、DAG、节点系统或模型服务。**

### 阶段 D — 执行并管理产物

**输入：** 已可执行的计划与获准的资源。

**Agent 要做：** 选择/调用工具，验证工具输入输出，跟踪步骤和失败原因；将素材、草案、成片和版本关联到对应任务、参考与意图记录，避免在多次重试中失去上下文。

**输出：** 可查看的产物、来源关系、执行状态与可核对的操作记录。

**建议的风险门槛（待批准）：** 涉及付费消耗、下载/执行外部代码、上传私密素材、覆盖文件等行为应有明确权限和可控边界；不做无限重试。

### 阶段 E — 评估成片与约束

将「工具运行成功」和「作品符合用户要求」分开。

**建议至少独立检查以下维度：**

- **目标达成：** 指定对象/动作/情绪/构图是否按意图改变。
- **保留完整性：** 未要求改变的对象、镜头、场景、身份、风格等是否受损。
- **连续性：** 局部修改前后，动作、时序、画面和声音（如有）是否衔接。
- **技术质量：** 可解码、画幅/时长等要求、明显生成缺陷与工具报错。
- **主观效果：** 美感、叙事与偏好不能仅靠自动分数代替用户判断。

**输出：** 「验收报告」应区分通过、未通过、无法验证、需要用户主观判断，附带依据；不可假定所有保留约束都能被视频生成模型严格保证。

### 阶段 F — 反馈、局部修订和共识更新

**输入：** 用户对当前产物的自然语言反馈，可选的时间段、区域、候选选择或参考对照。

**Agent 要做：** 把反馈映射为对现有意图记录的**增量变更**，保留既有确认，不将每句话视为全新任务；识别受影响的计划步骤和最小需要重做的部分。无法局部执行时须说明会连带改变哪些内容。

**输出：** 变更请求、受影响范围、继承与更新的约束、新产物 / 验收结果。下一轮应基于更新后的共识继续，而不是从空白提示词开始。

## 3. 一个贯穿全链路的案例

**已存在作品与参考视频。** 用户选中 **5–8 秒** 反馈：

> 人物转身太慢了，参考视频的动作更干脆。其他镜头保持不变。

| 环节 | Agent 应实现的行为 |
| --- | --- |
| A 理解 | 锁定 5–8 秒的转身；「更干脆」可能是起转时机、速度、停顿或结束姿态；其他镜头为保留约束 |
| B 分析 | 对照参考动作起止、姿态、速度变化和镜头对应关系；标注不确定的对应 |
| C 计划 | 先决定是否需要低成本澄清/预演；规划最小必要修改及边界检测 |
| D 执行 | 在可用工具能力范围内只修改必要范围，记录产物与来源 |
| E 评估 | **分别**核查转身达成度、其他镜头保真度、5/8 秒边界连续性 |
| F 迭代 | 用户说「再快一点」应沿用已确认的参考、范围与保留约束 |

**失败也必须可解释：** 若底层工具无法保证其他镜头不变，Agent 不应声称已经严格满足；应保留原版、指出风险，并提供可选方案（例如调整修改范围、换能力、改为可接受的近似效果）。具体可行方案需另行验证。

## 4. 可供原型验证的最小闭环（不是 V1 功能清单）

为验证「Agent 确实在创作」而非只会编排生成，建议用有限用例检验以下能力：

1. **目标与约束识别：** 输入一条创作指令与至多一个主要参考素材，能列清变化项、保留项和不确定性。
2. **必要时澄清：** 对影响关键方向的歧义提一个针对性问题；已明确时直接推进。
3. **计划与执行：** 形成可解释的有限步骤，调用至少一种真实媒体能力，保存中间结果与最终结果（模型/后端不限）。
4. **诚实评估：** 给出至少一项目标检查和一项保留项检查；不能验证时明确标记，不能把工具完成等同验收完成。
5. **一轮有效反馈：** 根据用户的局部反馈继承既有约束，形成修订结果或明确说明无法安全修订的原因。
6. **失败恢复：** 能分辨工具不可用、输入不合法、生成质量不足和约束冲突，停止无依据的重试并给出下一步选项。

这六项是**验证建议**，并非已经同意交付的 MVP 范围。原型可先采用短视频、关键帧、图片等较容易检查的素材，但不能靠替代物冒充尚未实现的视频能力。

## 5. 验证场景（尚无通过记录）

| 编号 | 场景 | 核心观测点 |
| --- | --- | --- |
| S1 | 模糊的一句话创作 | 真正关键的歧义是否被低负担澄清，非关键事项不反复追问 |
| S2 | 参考视频 + 新角色图片 | 镜头/动作/角色身份等维度是否被分别处理；不确定性是否标明 |
| S3 | 5–8 秒局部动作修订 | 目标动作、其他镜头保留、边界连续性能否分别核验 |
| S4 | 工具失败或配额不足 | 是否定位问题、停止无依据重试、保留可恢复状态 |
| S5 | 第二轮「再快一点」 | 是否继承上一轮被认可的范围、参考和禁止修改项 |

**评价方式：** 每个场景保留输入、预期、工具执行记录、产物、验收判断及用户反馈。先采用逐项可观察的人工评审；数值阈值和自动评分方法待实际实验后决定。

## 6. 边界：当前不因此确认

- 不承诺任意视频像素级保留、完美角色一致性或真实三维重建。
- 不确定必须使用真实 3D 白模、传统时间线、节点编辑器或某个 Agent 框架。
- 不把所有生成与编辑收束到一个 LLM URL / Key；媒体后端仍是可独立配置的能力。
- 不规定存储格式、工具协议、应用形态、本地/云端平台和具体 V1 交付清单。
- 不把「计划中的自动质检」写成已经存在且可靠的能力。

## 7. 下轮最值得作出的产品判断

1. **共识的最小语义单元：** 一条「必须保持不变」约束应绑定镜头、时间、对象、属性中的哪一层？更换作品版本后如何继承？
2. **澄清触发规则：** 哪些情况必须问、哪些能通过草案/候选解决、哪些可以作显式假设？
3. **验收责任划分：** 哪些可自动检测，哪些必须交给用户主观判断？如何表示「无法验证」？
4. **修改边界：** 在工具不能精确局部修改时，Agent 应如何在继续、替代、退回确认之间选择？
5. **执行授权：** 如何控制费用、隐私、模型依赖和危险操作，同时避免让普通用户陷入参数配置？

建议**优先讨论第 1 项：创作共识的表示与继承**。它是整个闭环避免「每轮重新开始」的前提。
