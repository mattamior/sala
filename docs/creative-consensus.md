# sala — Creative Consensus：创作共识的语义与跨轮继承

> **讨论稿 v0.1 · 2026-10-18 · 未经维护者逐条批准**
>
> 已批准的是「下一步优先设计创作共识机制」这一工作方向；本文中的字段、粒度、优先级规则、冲突处理与测试建议**尚未构成最终产品决策或数据协议**。不绑定具体技术栈、数据库、Agent 框架或 UI。

## 1. 目标与非目标

### 目标

让 Agent 在多轮创作中始终能回答：
1. 本次用户到底想改变什么，作用于哪个作品、版本、镜头/时间、对象和属性？
2. 哪些已被确认的内容必须保留？哪些仅是建议或 Agent 猜测？
3. 用户说「再快一点」「还是之前那个」「别动背景」时，指向哪个先前目标？
4. 当前计划会碰到哪些其他约束、参考依赖与无法保证的边界？
5. 结果的哪些约束已检查通过，哪些失败或根本无法检验？

### 非目标

- 不把所有自然语言变成永远有效的硬规则，不要求用户管理专业参数表。
- 不保证生成模型具备像素级局部编辑、任意镜头严格复刻或三维真值恢复。
- 不以聊天记录、Prompt 拼接或一个不断累加的自然语言摘要作为唯一真相。
- 不把 Agnir 项目级持久连续性直接用作视频工程内的创作状态。二者可以类比，但**是不同层级、不同生命周期的数据**。

## 2. 建议的语义模型：目标、约束、证据和状态分离

「创作共识」是某个作品/任务在给定时点的**有效创作意图快照**，并能回溯它如何由用户指令、参考、评价和修改产生。

**建议区分六种逻辑记录**（不是固定表结构）：

| 逻辑对象 | 职责 | 关键注意 |
| --- | --- | --- |
| Goal（目标） | 作品/本次改动期望达成的效果 | 可以主观、模糊，不等于工具参数 |
| Directive（指令/约束） | 改变、保留、允许、偏好的原子陈述 | 用户明示与 Agent 推断严格区分 |
| Anchor（指向） | 绑定作品版本、镜头、时间、区域、对象、属性 | 时间戳不可代替稳定语义指向 |
| Reference（参考） | 参考图/视频、当前或历史产物、用户选择及映射 | 区分可观察证据与推断 |
| Decision（决策） | 用户确认/否决或经澄清的选项 | Agent 的建议不会自动升格为用户确认 |
| Assessment（评估） | 某一产物版本对某条指令的检查结果 | 「生成成功」不等于「约束满足」 |

**最小语义单元建议为一条「带作用范围的、可判定来源的陈述」**，而不是一整个 Prompt，也不是一条孤立的时间线参数。

一条 Directive 至少需要表达：
- `id`：稳定标识，供反馈和评估引用；
- `intent`：希望改变 / 保留 / 允许自主 / 偏好；不同类型绝不可混作同等强度；
- `scope`：作品身份、来源版本、目标片段/对象/属性；可部分未知；
- `predicate`：期望或不得发生的变化，保留用户自己的表述；
- `strength`：明确硬约束、期望、软偏好或暂时假设；
- `source`：用户哪次表达、哪张参考图、哪次视觉指认或哪个 Agent 推断；
- `status`：待澄清 / 用户已确认 / 已拒绝 / 被更新取代等意图状态；
- `relations`：引用、覆盖、细化、冲突、继承、被取代的关系；
- `verification`：可评估的证据、检查方式、判定责任以及无法验证的原因。

## 3. 作用范围不能只有「5–8 秒」

同一条指令可能横跨以下层级：

- **作品/序列**：例如整条视频的氛围、节奏、画面比例。
- **镜头/片段**：例如第二镜头的运镜；「其他镜头不变」通常作用于一组排除目标的镜头。
- **时间/事件**：例如 5–8 秒人物转身；在编辑或重定时后原始秒数可能不再准确。
- **区域/实体**：人物、服装、背景、指定画面区域；同一个人物可能跨镜头出现。
- **属性/关系**：身份、运动速度、转身时机、构图、光线、景深、角色与摄影机关系。

**建议的定位原则：**
1. 优先使用「作品版本 + 镜头/实体等稳定语义标识 + 相对时间/事件」；保留原始绝对时间作为证据。
2. 修改时创建新产物版本，并维护新旧 Anchor 的对应关系；映射不确定时不静默把旧区间挪到新位置。
3. 跨镜头约束允许继承到子范围，但需明确在哪些维度适用；不得把局部指令错误提升为全片规则。
4. 无法确定「她」「这个镜头」「再快点」所指对象时，应借助当前选中对象、最近目标及上下文；如存在多个同等可能对象，先做一个有针对性的澄清。

## 4. 约束类型与强度（候选）

| 类型 | 例子 | 意义 |
| --- | --- | --- |
| Change（必须改变） | 「把转身改得更干脆」 | 目标需被评价是否实现 |
| Preserve（明确保持） | 「其他镜头保持不变」 | 禁止未经许可的连带修改；无法保证时须先说明 |
| Freedom（可自主） | 「灯光你来定」 | 仅为特定作用域、特定维度授予自主空间 |
| Preference（尽量满足） | 「更电影感一点」 | 容许解释和权衡，需保持用户原意 |
| Assumption（Agent 假设） | 「可能是转身速度偏慢」 | 用于规划，不可冒充用户确认的硬约束 |

**关键边界：**
- 「允许灯光自主发挥」不意味着允许更改人物身份或未涉及的镜头。
- 「只修改目标片段」是编辑授权边界，但输出后端可能重建非目标区域；若做不到严格保留，应标记无法满足/验证并让用户选择。
- 对未明确提及的属性，Agent 应尽量最小化副作用；**沉默既不是逐项用户确认的硬约束，也不是无限制改动许可**。
- 软偏好不能覆盖明确硬约束；用户后续确实可以明确修改旧约束，但不能由 Agent 凭猜测放宽。

## 5. 指令状态、产物状态与用户认可状态分别管理

避免「生成成功 → 约束已满足 → 用户已接受」这三个错误等号。

**意图状态建议：** `proposed` / `needs_clarification` / `confirmed` / `rejected` / `superseded`。

**执行状态建议：** `not_started` / `running` / `completed` / `failed` / `blocked`。

**评估状态建议：** `passed` / `failed` / `unverifiable` / `needs_user_review`。

用户对作品的接受/否定是独立事件，并不意味着所有隐藏属性都得到肯定；Agent 的技术检查结论也不能代替用户审美选择。状态名仅是示意，不代表 schema 已经批准。

## 6. 每一轮反馈的最小更新事务

建议每轮遵守以下流程：

1. **Resolve**：确定用户这句话针对哪个作品/版本、哪一条历史指令或对象；保留原话和上下文来源。
2. **Diff**：形成「新增、细化、撤回、替换」的候选差异，只触及本轮涉及的范围与属性。
3. **Conflict check**：检视与其他已确认指令及不可实现的操作边界是否冲突。
4. **Clarify when necessary**：关键指向模糊、硬约束矛盾、可能破坏已确认内容时先问；否则提出可见的解释并推进。
5. **Record candidate**：记录基于哪一版创作共识拟定，保留被取代的历史与拒绝的候选，不做不可追踪的原地覆盖。
6. **Plan and execute**：在允许范围内调用工具；保留可回退原版和相关素材引用。
7. **Assess and reconcile**：为每条受影响的指令绑定结果和验证状态，最终由新反馈更新有效快照。

多步骤或并行执行时，更新须比较基线版本；基线已变化则重新计算差异并检查冲突，**不能将过时的执行结果直接覆盖最新共识**。

## 7. 三轮连续案例：转身

初始作品版本 `V1`，用户选中第 5–8 秒人物转身，参考视频 `R1`。

| 约束 ID（例） | 类型 | 作用范围 | 表述 | 来源 / 状态 |
| --- | --- | --- | --- | --- |
| `C-01` | Change | `V1` 镜头 S2 的转身事件 | 转身更干脆，参考 `R1` | 用户明确提出；目标方向确认 |
| `C-02` | Preserve | `V1` 中 S2 以外的镜头 | 其他镜头保持不变 | 用户明确提出；保留硬约束 |
| `C-03` | Assumption | S2 转身动作属性 | 「更干脆」可能指起转更快、停顿更短 | Agent 推断；待核实 |

**第二轮：** 用户说「再快一点」。

- 如果只有 C-01 是当前活跃的速度/动作目标，候选更新为「相对当前版本进一步加快转身」，**继续继承 C-02 和参考 R1**。
- 「再快一点」并不自动允许整段视频加速，也不自动取消其他镜头保留要求。
- 若当前有多项相互竞争的「快」目标（转身、运镜、剪辑节奏），应询问指向哪项，不能猜。
- 生成新的 `V2` 前，可对用户说明将调整的目标；V2 完成后分别评估转身、非目标镜头和接缝连续性。

**第三轮：** 用户说「把其他镜头也一起改得更有节奏感」。

- 这是对旧 C-02 的潜在修订，不该继续机械理解成全片绝对不变。
- 但「其他镜头」究竟允许哪类改变（剪辑时长、运镜、人物动作、光色）仍可能关键；Agent 应检查是否与其他已确认的保留要求冲突，必要时只询问这一处。
- 新共识保留 C-02 被替代的历史，形成精确限定的新授权；不默默修改所有维度。

## 8. 两类冲突必须分开

**语义冲突：** 旧指令「镜头完全保留」，新指令「这个镜头的背景换掉」；先判定新意图是否明确替代旧约束，以及替代范围，而非简单「最新消息永远赢」。

**能力冲突：** 用户明确要求背景不变，但目前可用生成工具不能保证；**不能仅靠意图层面的确认消除技术限制**。应说明不能严格保证的部分，并提供保留原版、改换策略、接受近似等选项。

## 9. 对用户的呈现方式

内部可以维护细粒度记录，但普通用户无需看到约束对象、状态机或 JSON。

在关键节点，展示简短自然语言摘要即可，例如：

> 我会调整 5–8 秒人物转身的速度，继续按照参考视频保持动作方向。其他镜头不动；如果当前工具无法保证这一点，我会先告诉你。

可视化抓手用于辅助定位/确认差异，不意味着必须实现一个庞大的专业时间线编辑器。

## 10. 原型验收测试（尚未执行）

| 编号 | 输入/变更 | 应观测行为 |
| --- | --- | --- |
| CC-01 | 「5–8 秒转身更快，其他镜头不变」 | 产生目标与保留约束，且归属各自正确作用域 |
| CC-02 | 下一轮「再快一点」 | 准确追溯 C-01、继承 C-02、不误改全片 |
| CC-03 | 两个动作都可被解释为「快」 | 询问具体对象，而不是静默猜测 |
| CC-04 | 后续明确授权重做其他镜头 | 正确细化/替代旧保留约束，保留历史来源 |
| CC-05 | 编辑致原 5–8 秒挪位 | 能重映射语义事件；无法重映射就暴露不确定性 |
| CC-06 | 只能整片重生成，无法保持其他镜头 | 不谎报完成硬约束，执行前给出风险与可选路径 |
| CC-07 | 工具执行成功但目标或保留项失败 | 工具状态与创作评估状态分离 |
| CC-08 | 并行的旧版本任务晚于新反馈返回 | 检测基线落后，拒绝直接覆写当前共识 |
| CC-09 | 用户否决一个候选，再要求「刚才那个」 | 避免把被否决候选默认为当前已确认目标 |
| CC-10 | 参考视频与生成视频对不上镜头 | 标记映射不确定性并澄清/修正，不自行编造对应 |

这些是**建议的验收用例**，不是已经完成的测试。

## 11. 下一步需要维护者判断的设计分歧

1. **是否采用「目标 + 原子约束 + 引用/锚点 + 确认/评估分离」作为产品语义原则？**（推荐，具体数据模型之后再定。）
2. **默认保留程度：** 未说改变的区域是「尽力保持」还是「未经同意不得改变」？需要区分逻辑编辑边界与生成模型可保证程度。
3. **自动继承的边界：** 对「再快一点」等省略句，Agent 能在哪种确定度下自动继承而无须问？
4. **用户何时需要确认：** 能力不可保证、硬约束冲突和高成本执行之外，还应在哪些情况先确认？
5. **主观验收：** 一个用户只说「不错」是接受整个 V2、某个镜头，还是仅认可特定变化？默认应保守。

**本轮已决定的只有讨论优先级**；上述建议须在后续交流中逐项选择或修订。
